Developer guide
Everything needed to read this workspace from other software, or to be told when something happens in it. The API keys and Webhooks screens create the credentials; this page explains what to do with them.

Getting started
One REST API over HTTPS, JSON in and JSON out. Every path is versioned, and a breaking change gets a new version rather than a new shape at the old address.

Base URL
https://dealengine.cloud/api/v1
Version header
X-API-Version
Every response carries X-API-Version with the date this contract was fixed. Log it — when something changes, that value is what tells you which one you were talking to.

curl -H "Authorization: Bearer de_live_xxxxxxxx_…" \
  https://dealengine.cloud/api/v1/me
Copy
That call answers the four questions support otherwise has to look up: which workspace the key belongs to, whom it acts as, exactly which permissions and scopes it has, and its rate limit. Make it first.

Authentication
Send the key as a bearer token on every request. There is no session, no login call and no refresh — the key is the caller.

Authorization: Bearer de_live_a1b2c3d4_…
Copy
A key acts as one person. It inherits that person's role, permissions and record scope, so it can never see more than they can. Change their role and the key changes with it.
A read-only key is refused on every write, before any permission is even checked. Use one for anything that only reports.
The key is shown once, at creation, and only a hash is kept. Nobody — including us — can read it back. Lose it and mint a new one.
A key can be given an expiry when it is created. An expired key fails the same way an invalid one does — and so does every key acting as a person who has been deactivated or removed, or in a workspace that is not active, such as one suspended or deleted.
Every key starts de_live_ followed by the eight characters the Key column shows, so a credential is obvious on sight in a log or a config file.
Endpoints
28 of them today. Reads cover clients, contacts, deals, leads, quotations, contracts, activities, client feedback, account emails and saved reports; writes cover clients, deals and leads, plus the one result callback the Transparent integration posts. Campaigns, the reply inbox and Account management's own judgements — Growth ideas, account health and insights, program settings and account reviews — have no API yet. Invoices and payments are issued and recorded in Transparent, not here, so their old endpoints answer 410 Gone. Anything not listed here does not exist yet: a 404 on a path you expected is the honest answer, not an outage.

{
  "client":  { "companyName": "Acme Trading", "country": "SA" },
  "contact": { "name": "Sara Ali", "email": "sara@acme.example" }
}
Copy
Writes use input names, which are not the names GET returns. A client takes companyName, accountStatus, stageKey, industry, subIndustry, website, phone, companyEmail, taxNumber, addressLine, addressLine2, city, state, postcode, country, sizeBand, revenueBand, foundedYear, linkedinUrl, doNotContact, notes, ownerPublicId, accountManagerPublicId, salesAgentPublicId, parentPublicId, entityPublicId (the branch), defaultCurrency, defaultVatRate, defaultBreakdownSchemeKey and custom. A contact takes name, title, department, email, phone, mobile, linkedinUrl, preferredLocale, isPrimary and custom. ownerPublicId applies on a PATCH; a create is always owned by the key's own person, and a client linked to Transparent keeps its owner, the person who created it there. accountManagerPublicId also needs Assign account managers (accounts.assign), which exists only while Account management is on, and is refused when the person is not a member of the client's branch, or, on a client linked to Transparent (where the change is sent), when they are not paired with an active Transparent user. salesAgentPublicId needs only what the write itself needs, and is refused on the same three grounds (out of your scope, not in the branch, not paired on a linked client). A field name the API does not know is ignored, not refused — except by the Transparent result callback, which refuses it.

A deal takes name, clientPublicId, stageKey (GET /api/v1/pipeline lists the keys), amount, currency, probability, expectedCloseDate (YYYY-MM-DD), source, nextStep, competitor, dealType (new, existing, renewal or upsell), ownerPublicId, primaryContactPublicId, contacts (a list of publicId and role), origin, custom and tags. The client must already exist and be visible to the key — create it first with POST /clients — and every contact must work at that client. currency defaults to the workspace's base currency. While Marketing ROI is on, a new deal needs origin: kind legacy, outbound or referral (with referrerName and reason), or request with an open request's id. For history brought over from another system, a deal created straight into a won or lost stage takes closedAt (when it closed; now if left out) and lostReason. A PATCH changes only the fields it sends: null or an empty string clears a field, and moving a deal into a won or lost stage sends deal.won or deal.lost, as the board does.

A lead takes email, firstName, lastName, title, seniority, department, phone, linkedinUrl, companyName, website, industry, subIndustry, sizeBand, country, city, timezone, locale, status (new, contacted, replied, interested, qualified or lost), source, sourceDetail, consentBasis (legitimate_interest, consent or contract), notes, entityPublicId (the branch), custom and tags. POST answers 201 when it created the lead and 200 when the address was already there and it updated that lead; either way only the fields sent change. To check first, GET /api/v1/leads?email= finds one address. source defaults to api. An address on the do-not-contact list is kept with that status, an address on the workspace's own email domains is refused, and the lead endpoints answer 404 while Marketing is switched off.

Moving from another CRM: create each account with POST /clients, with its first contact, then add the rest of its people, then its deals with POST /deals and your prospects with POST /leads. Send an Idempotency-Key on every write — the old system's record id makes a good one — so a run that stops halfway can simply be started again without making duplicates. To find a record by its old id later, keep that id in a custom field.

Every list and every lookup is filtered by the key's own record scope before anything is returned. Clients, contacts, feedback and account emails are the accounts the key's person (or team) owns or looks after as account manager; deals, quotations, contracts and activities follow the deal's owner; leads follow their owner, and a lead nobody owns is visible to every key with Marketing access. A client nobody owns opens by its id for every key, as it does in the app; lists leave it out unless the key's person manages it. A record outside the scope responds exactly as one that does not exist — that is deliberate, because a distinguishable 403 would confirm the id was real.

Writes follow the same rules as the app's own forms. A field marked Required under Settings → Fields must be sent on a create and cannot be blanked by a PATCH. A Unique field refuses a value another record already holds. An email on one of the domains under Settings → Team → Your company's email domains is refused. Each comes back as invalid, with a code as the message — required:taxNumber, unique:taxNumber|Acme Trading (the other record's name appears only when this key can see it), internalDomain, unknownCurrency. A required or unique failure on the contact sent with a create is prefixed contact:.

Query parameters, all optional, all combinable.

For a sync loop, keep the timestamp of your last successful run and pass it as updatedSince, so a poll returns only what moved; without it you re-read the whole workspace on every cycle. Clients, deals, quotations and contacts come back newest change first. Invoices come back by issue date and activities by creation time, so on those two, page to the end rather than stopping at the first row you already have.

curl -H "Authorization: Bearer $DE_KEY" \
  "https://dealengine.cloud/api/v1/deals?status=open&updatedSince=2026-08-01T00:00:00Z&limit=200"
Copy
Paging
Every list returns the same envelope. total is the full count matching your filters, not the size of this page.

{
  "data": [ /* … */ ],
  "total": 137,
  "limit": 50,
  "offset": 0,
  "hasMore": true
}
Copy
Keep requesting while hasMore is true, adding limit to offset each time. An unparseable limit falls back to the default rather than erroring; the maximum is the part that is enforced. offset stops at 1,000,000 — a larger one is read as 1,000,000 and returns the same page again — so split a list longer than that with filters until each part is under a million rows.

Conventions
Ids are the public ids you see in the app's URLs. Internal database ids are never exposed.
Money is a string, always beside a currency code. JSON numbers are floating point, and a total that arrives as 1234.5599999 is worse than useless.
Dates are ISO-8601 in UTC, or null. Never a local-time string.
A missing value is null, never omitted — so you can tell "no value" from "a field I have not heard of".
Anything a workspace can rename travels as a stable key with the label beside it. Match on the key; show the label.
Countries are ISO 3166-1 alpha-2 codes — "SA", not "Saudi Arabia". Send either on a write and a code comes back; text that is not a country is stored as you sent it. Match on the code, and translate it for display yourself.
A contact's language travels as language — a code with no region, such as fr, zh or yue — and is null when they read the account's language. It can be any language the AI agents write in, not only the ten the app's screens use. On a create it is sent as contact.preferredLocale, and a code the product does not know is refused with invalid.
Some values are tidied on a write, the way country is: an email address is stored in lower case, and anything recognisably LinkedIn — a full address with tracking on it, a regional subdomain, or just the profile name — becomes one https://www.linkedin.com address, a bare name going under /in/ for a contact and /company/ for a client. A placeholder such as n/a is stored as null, and a value that is not recognisably LinkedIn is kept as sent.
A client filed under a parent account carries that parent as a `parent` object with its own id and name. It is null for the great majority of accounts, and null too when the parent sits in a branch this key cannot see. A client filed under a parent moves into the parent's branch, and its branch then changes only with the parent's: a write naming another branch for it is refused with `branch_inGroup`, and a parent in a branch the key's user is not a member of with `parent_branchNotYours`.
A deleted client, deal or quotation leaves the API: it drops out of every list and answers 404 by id. A deleted client's contacts go with it, and so does the timeline of a deleted client or deal. Restored from Recently deleted, the record comes back with a fresh updatedAt, so an updatedSince poll picks it up again — but its contacts and timeline return with their old updatedAt, so re-read them for that account. Nothing announces a delete — no webhook, no tombstone — so a mirror that must drop deleted records has to compare ids now and then. A deleted contact is gone for good.
A deal's amountBase is its amount in the workspace's base currency, converted at the rate in force when the amount was set — typed, imported or taken from a quotation — and it does not move when rates change later. "0.00" beside a non-zero amount means the deal's currency has no exchange rate set yet, never that the deal is worth nothing; it is converted as soon as the rate is set.

Errors
Every failure is the same shape: a machine-readable code and a sentence for whoever is reading a log at 2am.

{ "error": { "code": "forbidden", "message": "This key is read-only." } }
Copy
Code	Status	What it means
invalid	400	The body or a parameter was wrong. The message says which.
unauthorized	401	No key, or a key that is not valid, revoked or expired.
forbidden	403	The key is real but not allowed: read-only on a write, its role lacks the permission, or — on /feedback and /account-touches — Account management is switched off in the workspace.
notFound	404	No such record — or one outside this key's scope, which reads the same on purpose.
rateLimited	429	Too many requests. Wait for Retry-After.
serverError	500	Our fault. Retry with backoff; if it persists, tell us.
A message never names a record the caller was not allowed to see, and every authentication failure returns the same words — telling somebody a key is "revoked" rather than "invalid" confirms it was real, which is the one fact a thief wants.

Rate limits
600 requests per 60 seconds, counted per key. Generous enough that no honest integration notices, and every response tells you where you stand.

X-RateLimit-Limit: 600
X-RateLimit-Remaining: 594
X-RateLimit-Reset: 1786694460
Retry-After: 37          # only on a 429
Copy
Requests that arrive without a valid key are counted per IP address instead, so an unauthenticated flood is not free just because it never presents a credential. The windows are fixed rather than sliding: a burst straddling a boundary can briefly reach twice the limit, which is the price of a limiter that costs less than the endpoint it protects.

Idempotency
Send an Idempotency-Key header on any write and it becomes safe to retry. A network timeout leaves you not knowing whether the client was created; retrying with the same key answers that instead of creating a second one.

curl -X POST https://dealengine.cloud/api/v1/clients \
  -H "Authorization: Bearer $DE_KEY" \
  -H "Idempotency-Key: 8f2a1c4e-import-row-42" \
  -H "Content-Type: application/json" \
  -d '{"client":{"companyName":"Acme Trading"}}'
Copy
A repeat of the same key and the same body returns the first response verbatim, with X-Idempotent-Replay: true so your logs can tell a replay from a create. A key is remembered for at least 24 hours; after that it can be forgotten at any time, and the same request then runs again.
The same key with a different body is refused with 400 — that is a bug on your side, and quietly returning the old answer would hide it. A repeat that arrives while the first attempt is still running gets the same 400; retry it a moment later.
Up to 120 characters. Use something you can reproduce after a crash: a row number, a queue message id, a UUID you stored before sending.
Webhooks
The API lets you ask what happened. Webhooks tell you without being asked, which is the only way an integration reacts to a deal closing at 2am. Add an endpoint on the Webhooks screen; the signing secret is shown once, there.

Events
quotation.sent	A quotation was sent to a client — emailed from DealEngine, or marked as sent by hand.
quotation.accepted	A client accepted a quotation. The payload carries the accepted total, which can differ from the offered one when optional lines were declined.
quotation.declined	A client declined a quotation.
quotation.expired	A quotation passed its validity date without an answer.
deal.created	A deal was created — in the app or through the API. Deals brought in by an import do not send one each.
lead.created	A lead was added by hand or through the API. Leads from an import, a capture form or prospecting do not send one each.
deal.won	A deal was won — moved to a won stage, won by its client accepting the quotation, or won by a quotation marked won. The event an invoicing integration is usually waiting for.
deal.lost	A deal was lost.
approval.requested	A quotation was submitted for approval, or an approval chain moved on to its next approver.
approval.decided	An approver approved, rejected or asked for changes.
invoice.issued	An invoice was issued. It is immutable from this point, and this is the event an accounting integration usually waits for.
invoice.paid	An invoice was settled in full.
invoice.voided	An invoice was voided. The payload carries the reason.
payment.received	A payment was recorded against an invoice. Partial payments raise this each time, so read the invoice's standing rather than assuming it is settled.
feedback.received	Client feedback reached the account programs — from Transparent, an email read as feedback, or a rating clicked in an account email. It is sent by the account programs' own run, so only while Account management is on and up to about five minutes after the feedback arrived; a clicked rating waits 30 minutes in case it is changed, and feedback loaded as history never sends one. Duplicates and feedback a person said is not feedback are not sent.
touch.sent	An account program's email went out from the account manager's mailbox. The payload carries its words.
tags.changed	Tags were put on or taken off a record — from its page, a bulk change, an import or the API. The payload names the record, what was added, what was removed, and the tags it carries now.
An endpoint with no events ticked receives all of them. That is deliberate: the common case is "tell me everything", and a form where forgetting to tick a box silently delivers nothing is a trap.

What arrives
A POST with the event in a header and in the body. For quotation and deal events, data is the same resource shape the API returns for that record, so one integration can read GET /api/v1/quotations and receive quotation.accepted without learning two dialects. The four money events — payment.received included — all carry the invoice, with its payments, amountPaid and outstanding. The approval events carry an approval (status, reason, note, who asked, who approves, who decided) with the quotation inside it. feedback.received carries the feedback as GET /api/v1/feedback returns it, and touch.sent an account_email object as GET /api/v1/account-touches returns it. data is null when the record was deleted before the delivery was built.

POST /your-endpoint
Content-Type: application/json
User-Agent: DealEngine-Webhooks/1

Verifying the signature
The header carries a unix timestamp and an HMAC-SHA256 taken over the timestamp, a dot, and the raw request body, keyed with your endpoint's secret. Reject anything more than 300 seconds out of date.

Header format
X-DealEngine-Signature: t=<unix seconds>,v1=<hex hmac>
import { createHmac, timingSafeEqual } from "node:crypto";

// body must be the RAW request text, before any JSON parsing —
// re-serialising changes the bytes and the signature will never match.
function verify(secret, body, header) {
  const parts = Object.fromEntries(
    header.split(",").map((p) => p.split("=", 2))
  );
  const t = Number(parts.t);
  if (!Number.isFinite(t)) return false;
  if (Math.abs(Date.now() / 1000 - t) > 300) return false;

  const expected = createHmac("sha256", secret)
    .update(`${t}.${body}`, "utf8")
    .digest("hex");
  if (expected.length !== parts.v1.length) return false;
  return timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v1));
}

Two ways to get this wrong make the signature worthless: comparing with == instead of a constant-time compare, and skipping the clock check. The timestamp is inside what gets signed precisely so a captured request cannot be replayed forever.

Delivery and retries
Up to 7 attempts, waiting 1, 5, 30, 120, 360, 1440 minutes between them — roughly a day and a half in total, which is long enough to survive a receiver being down over a weekend.

Retried: any 5xx, 408, 429, a timeout, or a connection that never answered.
Not retried: any 3xx, or any other 4xx. That means the receiver understood and refused, or pointed somewhere else, and repeating it is noise until somebody fixes their end.
Delivery is at-least-once. Every payload carries a stable id that does not change across retries — store it and ignore a repeat. A duplicate you can drop is a much better failure than a deal nobody heard about.
After 20 consecutive failures an endpoint is switched off, with the reason kept on the row. Deliveries already waiting go out once you fix your end and press Resume, but events that happen while it is switched off are not queued for it at all — after a Resume, catch up through the API with updatedSince.
You have 8 seconds to answer. Return 2xx as soon as you have the payload and do the work afterwards; a slow handler will be retried while it is still running.
HTTPS only, and no credentials in the URL. This is a signed document about a customer's contract; plain HTTP would put it on the wire in clear.
The host must resolve to a public address. Private, loopback, link-local and cloud-metadata addresses are refused — on every attempt, not just when you save the endpoint — so a hook cannot be aimed at our internal network. A tunnel (ngrok and friends) is the way to receive on a laptop.
Redirects are not followed. A 3xx counts as a failed delivery, so publish the final URL rather than a shortener or a rewrite rule.
Testing
The Test button on the Webhooks screen sends a signed ping immediately. A 2xx answer shows its status code; any other status, a timeout or no answer shows as a failure. Use it before you trust an endpoint — finding out tomorrow that a URL had a typo is the failure this exists to prevent.
