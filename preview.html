01 — FIRST REQUEST

Getting started

DealEngine exposes one REST API over HTTPS. Requests and responses use JSON. Every path is versioned, and a breaking change gets a new version rather than changing the shape at the existing address.

i
Start with GET /me

It confirms which workspace the key belongs to, whom it acts as, its permissions and scopes, and its rate limit. Make this your first request.

cURL
curl -H "Authorization: Bearer $DE_KEY" \\
  https://dealengine.cloud/api/v1/me
↗One base URL

All API requests start with https://dealengine.cloud/api/v1.

◈Version awareness

Log the X-API-Version response header to know which contract you are using.

02 — SECURITY

Authentication

Send your API key as a bearer token on every request. There is no session, login call or refresh flow: the key is the caller.

HTTP header
Authorization: Bearer de_live_a1b2c3d4_…

How API keys work

  • A key acts as one person and inherits that person's role, permissions and record scope.
  • A key can never see more than the person it represents. If their role changes, the key's access changes too.
  • A read-only key is refused on every write before permission checks take place.
  • The full key is shown only once at creation. DealEngine stores a hash, so a lost key must be replaced.
  • Keys can have an expiry. Expired, invalid or revoked keys fail authentication.
  • Keys also fail when the person is deactivated or removed, or the workspace is inactive, suspended or deleted.
!
Keep your key private

Never put an API key in browser-side JavaScript, public repositories, screenshots or URLs. Store it in a server-side secret or environment variable.

Key format: de_live_ followed by the eight characters shown in the Key column.

03 — ENDPOINTS

API reference

There are 19 documented endpoints today. Read endpoints cover core CRM records and account activity. Writes are available for clients and the Transparent resource-request result callback.

!
Not every DealEngine feature has an API

Outreach (leads, campaigns and the reply inbox) and Account management judgements (Growth ideas, account health and insights, program settings and account reviews) currently have no API or webhook events. An undocumented path should be treated as unavailable, not as an outage.

i
Invoice and payment endpoint note

The guide overview mentions invoice and payment reads, and documents invoice-related filters and webhook events, but the current 19-row endpoint table does not list dedicated invoice or payment GET paths. This reference does not invent those paths.

ENDPOINT GROUP · CLIENTS

Clients

Read and manage client accounts. The create request can include the client's first contact in the same call.

PATCH behaviour

Only sent fields change; omitted fields stay as they are. Custom values are merged over existing values. The body uses the same input names as create, not the GET response shape.

Ownership and assignment rules

  • ownerPublicId applies on PATCH. A create is always owned by the person represented by the key.
  • A client linked to Transparent keeps its Transparent-side owner.
  • accountManagerPublicId requires accounts.assign (available only while Account management is on). The person must belong to the client's branch and, for a Transparent-linked client, be paired with an active Transparent user.
  • salesAgentPublicId needs the permission required by the write and is subject to the same scope, branch-membership and Transparent-pairing checks.
  • Unknown field names are ignored, not rejected.
ENDPOINT GROUP · CONTACTS

Contacts

People at the accounts the key can see. Contact visibility follows the same account scope as the related clients.

GET/api/v1/contactsList contacts.
GET/api/v1/contacts/{id}Retrieve one contact by public ID.
ENDPOINT GROUP · DEALS

Deals

Read deals visible to the key, following the deal owner's scope.

GET/api/v1/dealsList deals, newest change first.
GET/api/v1/deals/{id}Retrieve one deal by public ID.

Deal amount fields

amountBase is converted to the workspace's base currency using the rate in force when the amount was set. It does not change when exchange rates change later. A value of 0.00 beside a non-zero amount means no exchange rate is configured yet; it does not mean the deal is worth zero.

ENDPOINT GROUP · QUOTATIONS

Quotations

Read quotations visible to the key, following the deal owner's scope.

GET/api/v1/quotationsList quotations, newest change first.
GET/api/v1/quotations/{id}Retrieve one quotation, including its acceptance record if it has one.
ENDPOINT GROUP · CONTRACTS

Contracts

Read contracts visible to the key, ordered by soonest-ending first — useful for renewal lists.

GET/api/v1/contractsList contracts.
GET/api/v1/contracts/{id}Retrieve one contract, including renewal terms.
ENDPOINT GROUP · ACTIVITIES

Activities

Read the timeline: notes, tasks, calls, meetings and system-written rows such as stage changes and quotation events.

GET/api/v1/activitiesList timeline activities, newest first.

Activities follow the deal owner's scope. For a key that can see every deal, the timeline also includes account-level activities.

ENDPOINT GROUP · ACCOUNT MANAGEMENT

Feedback

Read client feedback at accounts the key can see. Sources include Transparent, emails read as feedback and ratings clicked in account emails. Duplicates and feedback a person said is not feedback are excluded.

GET/api/v1/feedbackList feedback, newest first.Account management
ENDPOINT GROUP · ACCOUNT MANAGEMENT

Account touches

Read emails written by account programs at accounts the key can see, including status and reason. Subject and body are returned only for an email that was sent.

GET/api/v1/account-touchesList account-program emails, newest first.Account management
ENDPOINT GROUP · WORKSPACE

Tags

Read the workspace tag library. Each tag includes its ID, name, colour, group, applicable record types and archived state. Resources also carry their own tags as a list of ID, name and colour. Client POST and PATCH accept tags as a list of names.

GET/api/v1/tagsList the workspace tag library.
ENDPOINT GROUP · TRANSPARENT

Transparent integration

Read a resource request by Transparent's own ID, then post the result back to DealEngine.

GET/api/v1/transparent/resource-requests/{transparentId}Retrieve one resource request.
POST/api/v1/transparent/resource-requests/{transparentId}/resultPost the answer to a resource request.deals.edit

The result callback requires a non-read-only key and deals.edit. Unlike normal client writes, unknown field names in this callback are refused.

04 — ACCESS CONTROL

Record scope

Every list and lookup is filtered by the key's record scope before data is returned.

ResourceScope applied
Clients, contacts, feedback, account touchesAccounts the key's person or team owns or looks after as account manager.
Deals, quotations, contracts, activitiesDeal owner's scope.
Invoices and paymentsBranches the person belongs to, with invoices.view.

A client nobody owns can be opened by ID for every key, as in the app, but lists leave it out unless the key's person manages it. A record outside scope returns the same response as a record that does not exist. This intentionally prevents callers from confirming that an inaccessible ID is real.

Incremental sync

Store the timestamp of your last successful run and pass it as updatedSince to retrieve only changed records. Without it, each poll reads the full matching set again.

cURL · Sync deals
curl -H "Authorization: Bearer $DE_KEY" \\
  "https://dealengine.cloud/api/v1/deals?status=open&updatedSince=2026-08-01T00:00:00Z&limit=200"
!
Two lists need full pagination

Invoices are ordered by issue date and activities by creation time. For these two, page to the end rather than stopping at the first row already seen.

06 — LARGE DATASETS

Pagination

Every list uses the same response envelope. total is the full count matching your filters, not just the number of rows on the current page.

JSON · List response
{
  "data": [ /* records */ ],
  "total": 137,
  "limit": 50,
  "offset": 0,
  "hasMore": true
}

Keep requesting while hasMore is true, increasing offset by limit each time. An unparseable limit falls back to the default; the maximum is enforced.

ParameterDefaultRule
limit50Maximum 200 rows.
offset0Maximum effective offset is 1,000,000.

Offsets above 1,000,000 are read as 1,000,000 and return the same page again. Split datasets larger than one million rows with filters until each part is below that threshold.

07 — DATA FORMAT

Conventions

Public IDs

IDs are the public IDs shown in app URLs. Internal database IDs are never exposed.

Money

Money is always a string, accompanied by a currency code. JSON floating-point numbers are not used for money.

Dates

Dates are ISO-8601 in UTC, or null. Never a local-time string.

Null values

A missing value is null, never omitted.

Stable keys

Renamable values are sent as a stable key with a label. Match on the key; show the label.

Countries

Country codes use ISO 3166-1 alpha-2, such as SA. On writes, a code is returned; non-country text is stored as sent.

Contact language

preferredLocale is a language code without a region (for example fr, zh or yue). Unknown codes are refused with invalid.

Normalised values

Email is stored lowercase. Recognisable LinkedIn URLs are normalised to a linkedin.com profile or company URL. A placeholder such as n/a is stored as null.

Parent accounts

A client under a parent carries a parent object. A child moves into its parent's branch, and its branch changes only with the parent. Naming another branch is refused with branch_inGroup; a parent in a branch the key's user does not belong to is refused with parent_branchNotYours.

Deleted records

Deleted clients, deals and quotations disappear from lists and return 404 by ID. A deleted client's contacts and the timeline of a deleted client or deal disappear too. Restoring a record gives that record a fresh updatedAt, but its contacts and timeline retain their old timestamps. Deleted contacts are gone permanently.

!
Deletes do not emit events

No webhook or tombstone announces a deletion. A mirror that must remove deleted records needs to compare IDs periodically.

08 — TROUBLESHOOTING

Errors

Every failure has the same response shape: a machine-readable code and a human-readable message.

JSON · Error response
{
  "error": {
    "code": "forbidden",
    "message": "This key is read-only."
  }
}
CodeHTTPMeaning
invalid400Request body or parameter is wrong. The message explains which.
unauthorized401Missing, invalid, revoked or expired key.
forbidden403Read-only key on a write, missing permission, or Account management disabled for feedback/account-touches.
notFound404Record does not exist or is outside the key's scope.
rateLimited429Too many requests. Wait for Retry-After.
serverError500Server-side failure. Retry with backoff; contact support if it persists.

Authentication failures use the same wording so a caller cannot distinguish a revoked key from an invalid one. Out-of-scope records intentionally look like missing records.

Validation examples

Required or unique field failures return invalid, with messages such as required:taxNumber or unique:taxNumber|Acme Trading. Other documented validation codes include internalDomain and unknownCurrency. A contact validation failure during client creation is prefixed with contact:.

09 — CAPACITY

Rate limits

Each API key is limited to 600 requests per 60 seconds. Responses tell you where you stand.

600requests / 60 seconds
Per API keyFixed window
HeaderPurpose
X-RateLimit-LimitMaximum requests in the window.
X-RateLimit-RemainingRequests remaining in the current window.
X-RateLimit-ResetUnix timestamp when the window resets.
Retry-AfterSeconds to wait; present on a 429 response.

Requests without a valid key are counted per IP address. Windows are fixed, not sliding, so a burst crossing a boundary can briefly reach twice the stated limit.

10 — SAFE RETRIES

Idempotency

Send an Idempotency-Key header on any write to make retries safe. If a network timeout leaves the result unknown, retrying with the same key and body returns the original response instead of creating a duplicate.

cURL · Idempotent create
curl -X POST https://dealengine.cloud/api/v1/clients \\
  -H "Authorization: Bearer $DE_KEY" \\
  -H "Idempotency-Key: 8f2a1c4e-import-row-42" \\
  -H "Content-Type: application/json" \\
  -d '{"client":{"companyName":"Acme Trading"}}'
  • Same key and same body: first response is returned verbatim with X-Idempotent-Replay: true.
  • Same key with a different body: 400 error.
  • A repeated request while the first is still running: 400 error; retry a moment later.
  • Keys are retained for at least 24 hours, then may be forgotten.
  • Maximum key length is 120 characters. Use a reproducible value such as a queue message ID or stored UUID.
11 — EVENT-DRIVEN INTEGRATIONS

Webhooks

The API lets you ask what happened. Webhooks notify your system when an event occurs. Add an endpoint from the Webhooks screen; the signing secret is shown once.

Available events

quotation.sentquotation.acceptedquotation.declinedquotation.expireddeal.wondeal.lostapproval.requestedapproval.decidedinvoice.issuedinvoice.paidinvoice.voidedpayment.receivedfeedback.receivedtouch.senttags.changed

An endpoint with no events selected receives all events. That is the default.

Webhook request

DealEngine sends a POST with the event in a header and in the JSON body.

HTTP headers
Content-Type: application/json
User-Agent: DealEngine-Webhooks/1
X-DealEngine-Event: quotation.accepted
X-DealEngine-Signature: t=1786694400,v1=6b1f…
JSON · Payload shape
{
  "id": "evt_01KZXHHDRSJKBGB4M67F7M3CSE",
  "event": "quotation.accepted",
  "occurredAt": "2026-08-13T09:01:37.710Z",
  "workspace": { "id": "01KZR0…", "name": "Future Group KSA" },
  "data": { "object": "quotation", "id": "01KZ…", "status": "won" }
}

For quotation and deal events, data uses the same resource shape returned by the API. Money events carry the invoice, including payments, amountPaid and outstanding. Approval events carry approval details and the quotation. Feedback and account-touch events use the same shapes as their corresponding GET endpoints. data is null if the record was deleted before delivery was built.

Verify the signature

The signature is an HMAC-SHA256 over the timestamp, a dot, and the raw request body, keyed with your endpoint secret. Reject timestamps more than 300 seconds out of date. Verify the raw body before JSON parsing or re-serialising it.

Node.js · Signature verification
import { createHmac, timingSafeEqual } from 'node:crypto';

// body must be the raw request text, before JSON parsing.
function verify(secret, body, header) {
  const parts = Object.fromEntries(
    header.split(',').map((p) => p.split('=', 2))
  );
  const t = Number(parts.t);
  if (!Number.isFinite(t)) return false;
  if (Math.abs(Date.now() / 1000 - t) > 300) return false;

  const expected = createHmac('sha256', secret)
    .update(`${t}.${body}`, 'utf8')
    .digest('hex');
  if (expected.length !== parts.v1.length) return false;
  return timingSafeEqual(Buffer.from(expected), Buffer.from(parts.v1));
}
!
Do not weaken signature verification

Use a constant-time comparison and enforce the timestamp window. Re-serialising the JSON changes the bytes and causes verification to fail.

Delivery, retries and endpoint health

  • Up to 7 attempts, with waits of 1, 5, 30, 120, 360 and 1,440 minutes between attempts.
  • Retried: 5xx, 408, 429, timeout or connection failure.
  • Not retried: 3xx and other 4xx responses.
  • Delivery is at-least-once. Store the stable event ID and ignore duplicates.
  • After 20 consecutive failures, the endpoint is switched off. Fix it and press Resume; events occurring while it is off are not queued. Catch up through the API with updatedSince.
  • Respond within 8 seconds. Return 2xx once the payload is received, then process asynchronously.
  • HTTPS only, no credentials in the URL, public host address required, and redirects are not followed.

Test your endpoint

The Test button on the Webhooks screen sends a signed ping immediately. A 2xx response confirms the endpoint answered successfully. Test before relying on production delivery.
